# PickPico 60 個能力的入口分類建議

日期：2026-09-12。狀態：使用者已確認；0.16.75（112）依此範圍實作。測試與發布狀態見 releases/0.16.75.md。

## 最終架構與本輪實作範圍

採用混合入口：18 個常用／共用能力直接提供完整參數，4 個能力沿用既有入口，其餘 38 個在 command_run 提供「ID＋短用途」索引。AI 一開始可知道全部 60 個能力的存在，不需要先搜尋才知道能做什麼。直接能力不在短索引再寫一遍完整說明。

第一版保留目前 12 個管理／探索入口，所以合計 30 個頂層工具。這個數量在本輪固定，先以總任務成本與成功率驗收，不在實作途中繼續擴增或任意合併。原有直接工具能沿用就沿用，新入口命名保持一致；動態 ID 保留相容。

正常路徑固定為：

1. 已有直接工具：看完整參數後直接使用。
2. 動態能力：從短索引選 ID → capability_status 精確取得輸入規格與目前可用狀態 → command_run。capability_status 本輪需新增 inputSchema 與必要呼叫提示，不能沿用目前只有描述／狀態的回覆就宣稱可直接呼叫。
3. 已知且規格未變：沿用已取得參數，不強制再次查詢。執行端仍驗證當下可用狀態。
4. 不知道選哪個：才使用 capability_search，以 1–3 個英文關鍵字保留動作意圖；精確 ID 不做模糊擴展。

所有入口共用原本的能力實作與本機核准政策。能力名稱使用固定選項並由伺服器驗證，不能只在說明裡列名。直接入口的參數不能退化成任意 JSON。

本輪一起完成的防呆與節流：

- 統一檢查必填欄位、型別、範圍與未知欄位；錯參數在操作及核准之前拒絕。
- 畫面動作核對觀察版本與唯一目標；無效 path 不退回選其他節點。已有正確前景時不先回首頁。
- 共用成敗判斷；區分操作成功、失敗、等待人與結果不明。取得過去失敗紀錄本身仍可成功。
- 精簡畫面、指南與能力狀態的預設回覆；歷史預設摘要；檔案／程序輸出支援接續讀取，避免反覆回傳全部內容。
- 人類求助提供可追蹤 requestId 與等待狀態，讓求助查詢可以實際接續。新入口採先交付 ID 的流程，舊等待行為保留相容。
- 純查詢入口標示真實標準行為提示；混合執行入口不宣告全部只讀。上游是否核准仍由上游決定。
- 保留使用者要求的模型型號顯示，所有新舊入口一致處理。舊客戶端與目前工作目錄既有修復需一併考量，不能覆蓋或退回。

本輪沿用 phone.wake／phone.home 的現有分工，不另新增準備手機工具，不修改本機核准政策。直接清通知等能走專用能力的任務，不先解鎖或進 App。操作指南按需讀，不強制每項日常能力執行前重讀。

完成條件：60 個能力不遺漏；18 個直接能力具完整有效參數；38 個索引均能精確取得規格並執行；既有入口保持相容；缺文字不清空、舊畫面不誤點、失敗不報完成、結果不明不誘導重送。以固定任務比較呼叫數與回傳大小，並進行相應測試與實機驗證；沒有其他模型實测就不宣稱 Gemini 成功率或上游拒絕率已改善。

本次重新讀取連線 MCP 的 capability_list，確認共有 60 個能力，並對照工作目錄 CommandRuntime 與 McpToolRegistry。分類表已檢查 60 個 ID 不重複、不遺漏。前一輪的已提交／手機／未提交版本差異，見同目錄 mcp-tool-audit-2026-09-12.md。

## 建議分配

- **直接：18 個。** 包含跨任務共用步驟、原先保留的手機狀態／拍照，以及使用者指定加入的五個能力。AI 一開始就看到獨立工具及完整參數。
- **動態：38 個。** 任務需要時探索；已取得能力 ID 與參數後可以直接呼叫，不要求每次重搜。
- **既有：4 個。** 已有對應頂層查詢工具，直接沿用，避免重複增加入口。

使用者已修正選擇原則：優先直接提供「跨任務共用、但通常不會寫在使用者要求裡的步驟」，而不只是看任務名稱或單一能力是否熱門。以下為修訂討論稿；新增 phone.wake、phone.home、human.help.status 為共用流程建議。使用者另指定的四組共五個能力已改為直接。這**不是根據完整使用紀錄計算的頻率排行榜**。手機回報能力 available 也不代表本次逐一驗證功能成功。

目前精簡清單有 12 個頂層工具；本輪保留，再加入這 18 個直接能力，合計 **30 個入口**。四個「既有」已包含在原本 12 個裡，不重複計數。其他管理入口精簡及準備工具整合留待量測後評估，不混入本輪。其餘能力仍保留原動態 ID 供舊客戶端使用；搜尋結果優先告知已有的直接工具，不把同一能力當成兩個候選。

第一版不為了湊到任意入口數量而移除必要管理工具。後續比較初始規格大小、整個任務總用量、完成率及錯誤次數，再決定哪些管理入口可按需載入。

## 短英文搜尋的約定

使用者照常說中文。AI 呼叫 capability_search 時，預設轉成 1–3 個英文關鍵詞，保留必要動作，例如 calendar list、calendar create、clipboard read、clipboard write。避免禮貌句、背景描述、無关字詞；只有名詞會無法分辨讀取與修改，不能把短詞理解為只留一個名詞。

若已知精確能力 ID，直接查該 ID，例如 calendar.list。精確 ID 應走精確比對，回一個能力，不再依每個片段擴展出大量候選。若已取得當前版本所需參數，無須再次搜尋。

建議工具說明用一句話表達：
> Use 1–3 English keywords, preserving the action (e.g. calendar list, clipboard read). If known, use the exact capability ID.

這是呼叫約定，不是遇到中文字就拒絕服務。服務端仍應支援常見中文、別名与合理修正；能力暫時不可用時回設定需求，不把它說成不存在。搜尋少字後仍須修正「查看排到刪除」「開相機排到拍照」的排序。

## 動態能力不能讓模型自行猜接續方式

- 聯絡人、通知、行事曆清單：回傳真實 ID，附必要的後續呼叫方式。
- 程序啟動：同時讓模型知道輸出與停止的參數。
- 人類求助：應先取得可追蹤 ID，再等待／查詢，不能逾時後連 ID 都拿不到。
- 更新：清楚區分檢查、下載安裝、等待本人操作與已安裝完成。
- 操作指南：搜尋只回相關指南摘要與版本，需要時讀全文；不要求每次直接工具呼叫都重讀指南。
- 檔案、通知、音量等成組能力：可以按任務載入相關規格，但不代表自動執行整組操作。

## 直接提供的必要配套

直接工具必須有真正完整的輸入規格，並共用原本的能力實作、參數驗證、核准政策與成敗判斷。不能只是把 command_run 換名字，仍讓 AI 填任意 JSON。

ui.action、ui.type 與 ui.scroll 在推出前，要落實必填欄位、唯一目標與舊畫面檢查。直接提供不代表預先授權，也不取消當次動作應有的判斷。

工具描述與標準行為提示應符合實際效果；不能把所有直接工具一起標成只讀。畫面讀取與截圖回傳也要先縮減，否則減少探索步驟後，仍會在每次觀察浪費大量資訊。

型號顯示需求照既有決策保留；新增直接入口的規格與實作須一致帶入 agent，避免動態入口要求型號、直接入口卻漏掉。

## 共用步驟的判斷方法

共用不表示所有任務都要跑相同前置程序。應先選能完成任務的路徑，再準備該路徑需要的條件。

| 階段 | 共用能力 | 何時需要 |
| --- | --- | --- |
| 準備手機 | phone.wake、phone.home | 選定畫面操作路徑且螢幕／鎖屏狀態阻礙操作時 |
| 觀察當下狀態 | ui.inspect、screen.capture | 辨認畫面；動作後重用來驗證結果 |
| 找到與進入目標 | app.list、app.launch、url.open | 不知道正確 App、尚未到目標或從連結開始時 |
| 執行畫面動作 | ui.action、ui.type、ui.scroll | 目標不能直接透過專用能力完成時 |
| 求助與接續 | human.help、human.help.status | 真正需要人處理一步，再確認狀態接續任務 |

例如清通知：現有程式透過通知服務取得通知與 cancelNotification，這條路徑沒有先呼叫解鎖或切回首頁。正常路徑可以是 notification.list → 取得 notification.dismiss 規格 → 清除指定通知 → notification.list 驗證。通知權限或服務不可用時，再依錯誤決定設定／求助，不能把每次先解鎖當成必要操作。此處是原始碼路徑確認，未在本次實際清除通知。

相對地，在 App 裡填表，需要時先亮屏／處理解鎖，再觀察、找到 App 與欄位、輸入、重新讀取驗證。已在正確畫面時不應先回首頁，否則反而增加操作。

目前 phone.home 是「喚醒＋請系統解除鎖屏＋前往首頁」，遇到安全鎖屏可能回 requiresUserAction；請求送出不等於已解鎖。若後續設計單一「準備畫面操作」工具，應保留目前 App、僅做必要準備，並明確回 ready／等待本人／不可用。這是待評估的新工具，現有 60 能力裡沒有它。

camera.capture 與 phone.status 先保留前版直接建議；它們不被當成每個畫面流程的必要前置步驟。

## 下一步

此分界已確認並實作；後續效能驗收仍需實際模型任務量測。驗收應包含較容易錯呼叫的模型，記錄總呼叫數、總用量、選對能力比例及任務完成率；不能只看最外層工具清單變短或模型是否能產生合法 JSON。
