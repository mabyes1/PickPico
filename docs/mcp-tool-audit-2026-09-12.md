# PickPico MCP 工具使用體驗查核

查核日期：2026-09-12。目的：減少 AI 使用工具時的資訊負擔、錯誤呼叫與不必要的核准阻擋，並讓較容易誤解指令的模型也能穩定使用。

本次只做查核與隔離測試，未修改產品程式、安裝 APK、發布更新或提交 Git。以下優先序是討論建議，尚未實施。

**主要判斷**

目前「少量入口、按需探索能力」的方向值得保留。最大問題不是工具名稱太多，而是搜尋容易指錯路、參數限制未完整落實、畫面與歷史回傳過大，以及讀取和執行動作共用一個不透明入口。繼續增加長篇提醒，很難補足這些問題。

對較容易犯錯的模型，應把正確選項排好、給可直接使用的參數、在執行前攔下錯誤、回傳明確的下一步；不要要求模型靠閱讀更多規則自行補救。

**三個最容易造成真實誤操作的細節**

1. `ui.type` 宣告 `text` 必填，但 handler 使用 `optString("text", "")`。隔離測試省略文字仍進到 Android-facing 操作層；Android 實作也取預設空字串，再執行 SET_TEXT。這意味著在有效可編輯目標上有清空欄位的路徑。實機未執行這種破壞性驗證。`workspace.write` 和 `clipboard.set` 也有類似缺文字卻預設空字串的程式路徑。
2. `findNode` 收到找不到的 path 後會退回搜尋其他元件；後續 `matches` 比對文字、ID、說明、類別，卻不比對 path。若只提供無效 path，其他限制全空，可能選到第一個節點。正常存在但過時的 path，也沒有畫面版本來證明仍是原目標。僅增加「不要沿用舊 path」的說明不足以攔住模型錯誤。
3. 同名文字預設 `instance=0`，找不到唯一目標時沒有先回歧義。click 還可能向上尋找可點擊父節點。指南雖要求不要直接選第一個同名結果，但執行端沒有強制唯一性。需要明確回傳匹配數、實際操作目標與不匹配原因。

**隔離呼叫測試**

使用已提交的真實 registry/runtime/protocol 類別，以替身取代 Android 操作、政策狀態和畫面，沒有呼叫手機寫入動作。這些不是 Android 裝置端驗證。

| 輸入 | HEAD 實測 | 判讀 |
| --- | --- | --- |
| ui.type 缺 text | 進到操作層，isError=false | 應先拒絕 |
| ui.type 的 text=123 | 進到操作層，isError=false | 沒有嚴格執行字串型別限制 |
| phone.status 帶 typo=true | 進到操作層，isError=false；線上也接受 | additionalProperties=false 沒有完整落實 |
| ui.inspect 的 maxNodes=-1 | 進到操作層，isError=false | 入口未先按範圍拒絕；不等同於 Android 一定用 -1 執行 |
| 模擬 UI 回 performed=false | 外層 completed、isError=false | 成功／失敗封裝錯誤，工作目錄已有修復 |
| ui.action 的 action=tap | 拒絕，isError=true | 手寫 enum 檢查有效 |
| 不存在的 commandId | 拒絕，isError=true | 但缺少可修正的候選／查找提示 |
| arguments 傳 JSON 字串 | 被當成沒有 arguments，phone.status 照常執行 | 錯型別被靜默改成預設值 |

這八個案例展示的是「檢查不一致」，不是宣称所有能力都沒有檢查；日期範圍、數字 ID、部分 enum 和工作路徑已有專門檢查。

**降低上游不必要阻擋，實際能做什麼**

標準的工具行為提示目前缺失。MCP 的 `readOnlyHint`、`destructiveHint` 等有保守預設，而且只是提示；客戶端可不採信。補上真實、可由伺服器保證的提示，有助上游理解，但不能保證免核准。[MCP 工具規格](https://modelcontextprotocol.io/specification/2025-11-25/schema)、[MCP 官方對工具提示的說明](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)

可先做的事是把純探索／查詢入口說清楚，移除與該工具無關的能力羅列，讓每次呼叫的目標與效果可辨識。現在讀指南也透過能執行任意程序的 command_run，這是結構性的不透明；僅把 risk 字樣換得溫和，不會消除這個問題。

如果增設 `query` 一類的只讀入口，必须有伺服器白名單擋住寫入能力；不能只改名稱或宣告。UI 讀取可以不修改裝置，但讀到的仍可能是私人或外部內容；是否寫入與是否敏感，應分開表達。現有工作檔把部分讀取操作 risk 改為 read_only，可當成操作描述修正，不能視為所有資料已安全或使用者已授權。

本次沒有觀察到上游安全拒絕；因此「哪些描述真的導致拒絕」仍需後續同任務、同權限、不同工具版本的實測。不要以隱藏能力、宣稱普遍授權或繞過核准作為優化手段。

**對容易誤解的模型，應如何設計**

Google 官方目前也建議工具說明明確、參數使用具體型別、執行前驗證，並將活躍工具維持在有限數量；同時提醒支援的規格子集與過大／過深規格限制。這支持精簡入口方向，但不代表把所有能力塞進任意物件就會更可靠。[Gemini 官方函式呼叫說明](https://ai.google.dev/gemini-api/docs/function-calling)

建議測試兩個方向，再決定是否拆工具：

- 保留動態入口：改善搜尋、回完整可用的呼叫範本、統一驗證與錯誤、縮短回傳。這是改動較小的第一步。
- 少量常用的具體入口：例如畫面讀取與 UI 操作保留完整參數，其他能力仍按需探索；純查詢與寫入分流。比較多出的初始規格成本，是否能換到更少的後續探索與誤呼叫。

不建议直接展開全部 60 個工具。也不建议只有一個完全任意 JSON 的万能入口。入口數量應由完成同一需求的總成本與成功率決定。

未提交版本的指南範本已新增 `requiredCallerArguments:["agent"]` 提醒，但範本 arguments 本身仍不含 agent。較弱模型若直接照抄仍會失敗；應在相容層自動補已知型號，或明確區分「可執行範本」與「待填內容」。保留目前允許「unknown (model not exposed)」的設計，不要求模型編造型號。

**建議後續驗收方式**

先建立可重跑的小型任務集，固定工具版本、裝置狀態與模型型號；每項用多種繁體中文、簡體中文、英文及自然口語。至少涵蓋：查電量、讀通知、找聯絡人、查看／新增行程、開 App、截圖、找欄位、重名元件、舊畫面、缺參數、失敗後恢復、等待人類、輸出分段。

每個版本記錄：首次能力選對率、完成率、錯參數次數、無進展重試、總呼叫數、模型實際 token 用量、完成時間、使用者被打斷次數、上游拒絕原因。錯誤寫入必須另外統計，不能靠「大多完成」掩蓋。

優先驗收：讀行事曆不把寫入排前；缺文字不清空；舊 path 不改點別處；失敗不報完成；未知執行結果不重送；更短回覆仍能完成相同任務。格式正確不等於任務成功，因此不能只加 JSON 測試就宣布優化完成。
